# 计划审批与自适应排版合并实施规格

## 目标

在同一轮客户端更新中解决两个直接影响使用的问题：

1. 完整接入官方 Grok Build CLI 的计划审批请求，避免 `Plan approval could not be completed because the client disconnected`，并允许用户批准、要求修改或放弃计划。
2. 在保留现有毛玻璃、多颜色主题和自定义背景能力的前提下，借鉴参考页面的层级和空间组织，重新整理桌面端的新任务页、执行页与左侧导航。

本轮同时覆盖 Windows 桌面端、手机网页和 iPad 网页。Windows 安装包与便携包版本计划从 `0.1.2` 升至 `0.1.3`。

## 范围边界

本轮包含：

- `x.ai/exit_plan_mode` 直接请求和网关包装请求。
- 桌面、手机、iPad 的计划查看和审批。
- 多客户端首个有效答复生效，其他客户端同步关闭审批。
- 断线重连后恢复尚未完成的计划审批。
- 桌面端状态自适应首页和执行页排版。
- 桌面左侧栏的信息层级与密度优化。
- 现有手机单栏和 iPad 可收回三栏布局的兼容调整。

本轮不包含：

- `x.ai/ask_user_question` 等其他扩展交互协议。
- 新增或替换主题、背景图、头像、模型供应商功能。
- 原生 iOS/iPadOS 应用重写。
- 自动批准计划或关闭弹窗时自动拒绝。
- 全面复制参考产品的颜色、品牌、图标或功能入口。

## 问题一：官方计划审批

### 根因

当前 Electron 主进程只处理 `session/request_permission` 和 `x.ai/folder_trust/request`。官方 CLI 发出的 `x.ai/exit_plan_mode` 会进入未知反向请求分支并收到 JSON-RPC `-32601`。CLI 将审批失败视为客户端断开，保留 Plan 模式并等待重连后重新展示。

### 官方协议

客户端必须接受两种线格式：

```text
直接请求:  method = x.ai/exit_plan_mode
包装请求:  method = _x.ai/exit_plan_mode，真实 method 和 params 位于 params 内
```

归一化后的请求字段为：

```json
{
  "sessionId": "session-id",
  "toolCallId": "tool-call-id",
  "planContent": "# Plan"
}
```

响应严格使用官方定义：

```json
{ "outcome": "approved" }
{ "outcome": "cancelled", "feedback": "需要修改的内容" }
{ "outcome": "abandoned" }
```

空白修改意见不得提交为“要求修改”；空白 `feedback` 不写入响应。关闭窗口或客户端断线不产生任何审批响应。

### 主进程状态与路由

新增独立、可测试的计划审批协议模块，负责：

- 识别直接和包装方法。
- 解包并校验 `sessionId`、`toolCallId`、`planContent`。
- 构造三种合法响应。
- 生成用于客户端显示的安全数据，不暴露原始 JSON-RPC 包装。

主进程继续使用 JSON-RPC 请求 `id` 完成当前连接上的响应，同时保存 `toolCallId` 作为跨连接、跨客户端的稳定交互标识。待处理记录至少包含：

```text
requestId, sessionId, toolCallId, planContent, receivedAt
```

桌面 IPC 和手机控制服务使用同一条 `replyPlanApproval` 入口。第一个合法答复提交后：

1. 主进程向 CLI 返回对应结果。
2. 删除当前 `requestId` 的反向请求。
3. 广播包含 `requestId` 和 `toolCallId` 的 `interaction-resolved`。
4. 桌面、手机和 iPad 同步关闭匹配的审批窗口。

重复答复返回“审批已完成或失效”，不得向 CLI 发送第二次响应。

### 断线和重连

CLI 进程或传输断开时，渲染端保留可见计划内容，但将操作按钮设为等待重连；不得本地伪造结果。官方 CLI 重连并重放审批后，主进程按 `toolCallId` 将新 `requestId` 关联到原交互，更新按钮状态而不是创建第二个窗口。

如果收到官方 `interaction_resolved` 通知，则按 `toolCallId` 清理任何陈旧审批，即使本地保存的 `requestId` 已经变化。

### 桌面审批界面

使用独立模态窗口，不复用工具权限弹窗。窗口由以下区域组成：

- 标题和当前工作区/会话信息。
- 可滚动的 Markdown 计划预览。
- “提出修改意见”文本区，默认折叠或紧凑显示。
- 三个明确动作：“批准并执行”“提出修改意见”“放弃计划”。
- 提交中、已失效、等待重连和提交失败状态。

“批准并执行”是主操作。“提出修改意见”仅在文本非空时可提交。“放弃计划”使用危险操作样式并需要一次轻量确认。按 `Esc` 或点击关闭只隐藏窗口；待处理提示仍保留在任务状态区，可再次打开。

### 手机与 iPad 审批界面

手机使用接近全屏的底部面板或模态页，计划正文单独滚动，操作区固定在安全区域上方。iPad 在现有中间对话栏上方显示审批层，不改变左右栏开合状态。

移动端与桌面端使用相同的三种结果和校验规则。任一端提交后，其他端通过控制服务广播关闭对应审批。手机切后台、浏览器刷新或 WebSocket 重连后，由桌面控制服务重新发送仍待处理的审批快照。

## 问题二：状态自适应页面排版

### 设计原则

参考图只用于排版和视觉层级，不复制其深色主题。现有主题变量、毛玻璃表面、自定义背景位置和头像继续生效。

界面按会话状态切换布局，而不是让空白首页和执行页共用同一套密度：

- 无消息的新任务：突出输入和开始动作。
- 已有消息或任务执行中：突出对话时间线、工具步骤、最终回答和后续指令。

切换只改变 CSS 状态和已有元素位置，不重建连接、不清空输入、不丢失附件和待执行队列。

### 桌面新任务页

新任务页采用居中的内容列：

1. 简短欢迎标题。
2. 主输入框，位于首屏视觉中心附近。
3. 输入框内或紧邻输入框的工作区、模型、权限模式和附件入口。
4. 最多三个紧凑快捷入口，用于开始常见任务或打开已有功能；不增加营销说明。

顶部栏只保留当前任务标题和必要的全局操作。当前连接、工作区和模型状态以紧凑状态呈现，不再占据中央大卡片。输入框在新任务页可以更宽，但必须限制最大宽度，超宽屏不横向拉伸。

### 桌面执行页

发送第一条消息后切换到执行页：

- 对话时间线成为中央主区域。
- 每一步说明位于对应工具执行块之前。
- 工具结果保持可折叠，避免长输出挤压最终答案。
- 最终回答在本轮步骤结束后独立呈现。
- 输入框固定在底部内容列内，可继续发送、排队、修改或取消下一步指令。
- 任务状态、待执行队列和恢复草稿保持在输入框上方，但压缩无关留白。

自动滚动继续遵循“用户靠近底部才跟随”的现有规则；计划审批出现时不得强制改变用户当前滚动位置。

### 桌面左侧导航

左侧栏改为更清晰的三段：

1. 新建任务和工作区切换。
2. 按工作区分组的最近对话。
3. 底部账号、手机连接、设置和连接状态。

历史会话从独立功能入口提升为左侧栏的主要内容。模型/API、额度、扩展、任务监控等低频功能移入紧凑菜单或设置入口，不在左栏形成同等权重的长列表。

侧栏保留折叠能力。折叠后使用图标和工具提示，内容列获得空间；展开/折叠状态本地保存。长工作区名称、会话标题和路径使用省略与悬浮提示，不能撑宽侧栏。

### 手机与 iPad

手机保持单栏对话优先：新任务时输入区适度上移，但不使用桌面的大面积欢迎布局；开始执行后恢复底部固定输入。会话和控制仍通过覆盖面板进入。

iPad 保留现有自适应规则：竖屏使用左右抽屉，横屏使用可收回三栏。中间栏采用与桌面一致的新任务/执行状态切换，但不改变左右栏宽度、保存状态和安全区域逻辑。

### 响应式与可访问性

- 桌面内容列设定稳定的最小和最大宽度。
- 输入框、按钮、计划操作区不得因文字或加载状态改变整体尺寸。
- 图标按钮继续使用 Lucide，并提供 `title` 或可访问名称。
- 模态窗口管理焦点，关闭后回到触发入口。
- 手机触控目标不小于 40 像素，并处理 `safe-area-inset-*`。
- Markdown、代码、表格、长路径和长模型名称不得横向撑破容器。
- 所有主题下都要检查计划预览、禁用态、危险操作和焦点态对比度。

## 组件和文件边界

预计修改范围：

- `desktop/src/plan-approval-policy.js`：协议归一化、校验和响应构造。
- `desktop/src/main.js`：反向请求路由、待处理状态、IPC、移动端广播和重连关联。
- `desktop/src/preload.js`：桌面审批事件与回复 API。
- `desktop/src/renderer/index.html`、`renderer.js`、`styles.css`：桌面审批窗口与状态自适应排版。
- `desktop/src/mobile/index.html`、`app.js`、`styles.css`：移动审批界面和中间栏状态适配。
- `desktop/scripts/qa-desktop.js`：审批、新任务页和执行页的视觉 QA 场景。
- `desktop/test/*.test.js`：协议、控制服务、DOM 契约和布局策略测试。
- `desktop/package.json`：验证通过后升级版本至 `0.1.3`。

只有在状态判断出现重复且可独立测试时，才新增小型布局策略模块；不为了本轮改版拆分整个渲染器。

## 测试策略

实施遵循测试先行，每项生产代码修改前先观察对应测试以预期原因失败。

### 协议测试

- 直接和包装的 `x.ai/exit_plan_mode` 均能正确识别和解包。
- 请求接受 camelCase，并对必要字段缺失给出明确错误。
- 三种响应与官方 Rust 类型完全一致。
- 空白修改意见被拒绝，`feedback` 不产生空字段。
- `requestId` 与 `toolCallId` 分别承担连接内响应和跨连接恢复职责。

### 主进程与控制服务测试

- 计划请求不再收到 `-32601`。
- 桌面 IPC 和手机 WebSocket 都能在长任务仍运行时完成审批。
- 多客户端同时提交时只有第一个答复生效。
- 断线重放更新已有审批，不创建重复审批。
- 按 `requestId` 或官方 `toolCallId` 解析通知都能关闭陈旧界面。
- 普通权限和文件夹信任流程不回归。

### UI 契约测试

- 桌面和移动 HTML 包含计划预览、反馈和三个动作。
- 关闭审批不会发送结果。
- 新任务和执行状态使用明确、互斥的布局标识。
- 左侧栏折叠状态、输入内容、附件和排队指令在布局切换后保留。

### 视觉 QA

至少生成并检查以下截图：

- `1440x900` 桌面新任务页。
- `1440x900` 桌面执行页。
- `1440x900` 桌面计划审批（含长计划和反馈）。
- `390x844` 手机新任务和计划审批。
- `768x1024` iPad 竖屏计划审批。
- `1024x768` 与 `1366x1024` iPad 横屏三栏和计划审批。

截图必须确认：画面非空、文字和按钮无重叠、计划正文可滚动、操作区始终可达、主题背景正常、左右栏状态未被审批破坏。

### 回归与打包

- 运行全部桌面 Node 测试和后端 smoke test。
- 运行 Electron 桌面、手机和 iPad QA。
- 生成 `0.1.3` Setup 与 Portable 安装包。
- 检查安装包文件名、版本、SHA-256 和启动后的可见版本。

## 验收标准

满足以下条件才视为完成：

1. 官方 CLI 请求退出 Plan 模式时，桌面或移动端一定出现可操作的计划审批，而不是断连错误。
2. 批准、修改、放弃分别产生官方要求的响应，修改意见能返回模型继续规划。
3. 刷新、短暂断网或切换设备后，未完成审批能够恢复且不会重复答复。
4. 新任务页采用参考图式的中央输入层级；发送后平滑进入执行页，不丢失状态。
5. 左侧栏以工作区和会话为主，低频入口收敛，仍可访问全部现有功能。
6. 桌面、手机和 iPad 没有遮挡、溢出、重复消息或布局跳动。
7. 全量自动测试、视觉 QA 和 Windows 打包全部通过。
